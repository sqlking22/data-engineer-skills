# 需求分析最佳实践

> 本文沉淀团队在需求分析阶段的实战经验，配套 [SKILL.md](../SKILL.md) 一起使用。

## 1. 核心原则速查

| # | 核心原则 | 说明 |
|---|---------|------|
| 1 | **业务驱动，技术中立** | 需求聚焦业务价值，不提前限定技术方案 |
| 2 | **明确数据口径** | 每个指标必须有唯一、清晰的计算公式 |
| 3 | **粒度先于指标** | 先确定数据粒度，再设计指标 |
| 4 | **边界清晰** | 明确"做什么"和"不做什么"，避免范围蔓延 |
| 5 | **可验证性** | 每个需求必须有可验证的验收标准 |
| 6 | **书面留痕** | 重要澄清必须有书面确认，不依赖口头约定 |
| 7 | **变更受控** | 任何变更都需评估影响并经过审批 |

## 2. 反模式与避坑指南

### ❌ 反例 1：需求描述模糊

```
用户："我们想要更好的数据分析"
```

✅ 正例：

```
业务场景：电商运营团队
分析目标：销售业绩监控（GMV、订单量、客单价）
数据来源：MySQL 订单库（orders、order_items、users）
使用方：销售运营部（日报）、财务部（月报）
时效要求：T+1 早上 8 点前
特殊要求：需要追踪用户等级变化历史
```

💡 **为什么**：模糊需求会导致大量返工。5 段式公式（场景/目标/来源/使用方/要求）能消除 80% 的歧义。

---

### ❌ 反例 2：指标口径未定义

```yaml
- name: "GMV"
  description: "成交总额"
```

✅ 正例：

```yaml
- name: "GMV"
  alias: ["成交总额", "交易额"]
  definition:
    formula: "SUM(订单金额)"
    filter: "status IN ('paid', 'completed')"
    exclude: "退款订单金额、运费、优惠券"
    unit: "元"
    precision: 2
  data_sources:
    - table: "orders"
      column: "order_amount"
```

💡 **为什么**：同一指标在不同团队可能有不同理解。明确公式、过滤、排除项后，才能保证跨团队口径一致。

---

### ❌ 反例 3：粒度未声明

```yaml
fact_table:
  name: "fct_orders"
  measures: [order_count, total_amount]
```

✅ 正例：

```yaml
fact_table:
  name: "fct_orders"
  grain: "订单项级别（每行代表一个订单中的一个商品项）"
  measures: [quantity, item_amount]
  pk_strategy: "order_item_id（自然键）"
  derived_facts:
    - "订单级指标通过 order_id 聚合得到"
```

💡 **为什么**：粒度不明确会导致后续建模时混淆事实表和聚合表，后期修复成本极高。

---

### ❌ 反例 4：边界未划分

```
需求：建设数据仓库
```

✅ 正例：

```yaml
scope:
  included:
    - 订单相关数据
    - 用户主数据
    - 销售分析报表
  excluded:
    - 营销活动数据（v2.0 再做）
    - 物流数据（独立项目）
    - 财务对账（财务团队负责）
  assumptions:
    - 数据源在 MySQL 主库
    - 业务核心时段 9:00-18:00
```

💡 **为什么**：未划清边界的项目几乎必然超期。"做什么"和"不做什么"同等重要。

---

### ❌ 反例 5：需求变更无记录

```
业务方："之前说的那个需求要改一下"（无书面记录）
```

✅ 正例：

```yaml
# change_log.yaml
- date: "2024-01-20"
  type: "范围变更"
  description: "增加商品类目分析维度"
  before: "仅支持商品级分析"
  after: "支持商品 + 类目双维度"
  impact:
    modeling: "需要新增 dim_category 维度表"
    etl: "新增类目同步任务"
    timeline: "+3 人天"
  approved_by: "产品经理-张三"
  approval_date: "2024-01-20"
```

💡 **为什么**：口头变更在 3 个月后无人能记得。书面记录是项目可追溯、可复盘的基石。

## 3. 需求描述模板

### 3.1 5 段式需求公式

```
[业务场景] + [分析目标] + [数据来源] + [使用方] + [特殊要求]

示例：
"我们是电商平台（业务场景），
 需要分析销售业绩（分析目标：GMV、订单量、客单价），
 数据来自 MySQL 订单库和用户库（数据来源），
 主要给运营团队做日报（使用方），
 需要保留用户等级变化历史（特殊要求）"
```

### 3.2 完整需求包 YAML 模板

```yaml
requirement_package:
  version: "1.0"
  metadata:
    project_name: "电商销售分析数仓"
    generated_by: "requirement-analyst"
    generated_at: "2024-01-15T10:00:00Z"
    confirmed: false           # 业务方是否已确认
    confidence_score: 0.85     # 置信度 0-1
    
  business:
    domain: "电商"
    subdomain: "销售"
    owner: "销售运营部"
    goal: "监控销售业绩，支持运营决策"
    success_criteria:          # 可验证的成功标准
      - "日报自动生成，早上 8 点前产出"
      - "数据准确率 > 99.9%"
      - "异常自动告警"
    kpis: ["GMV", "订单量", "客单价"]
    
  functional:
    entities:                  # 业务实体
      - name: "订单"
        type: "业务实体"
        attributes: ["order_id", "user_id", "amount", "status"]
    metrics:                   # 指标定义
      - name: "GMV"
        formula: "SUM(amount) WHERE status IN ('paid', 'completed')"
        dimensions: ["日期", "地区", "用户等级"]
    dimensions:                # 分析维度
      - name: "日期"
        type: "时间维度"
        granularity: ["日", "周", "月"]
    reports:                   # 报表需求
      - name: "销售日报"
        user: "销售运营部"
        frequency: "每日"
        
  non_functional:
    performance:
      query_response_time: "< 5s"   # 95% 查询
      data_freshness: "T+1 8:00"
      concurrent_users: 50
    security:
      pii_fields: ["user_phone", "user_email"]
      encryption: "MD5 + 脱敏"
      access_control: "按部门 RBAC"
    compliance:
      - "符合《个人信息保护法》"
      
  technical:
    preferred_stack: ["AnalyticDB MySQL", "MaxCompute"]
    existing_systems: ["MySQL 订单库", "Redis 缓存"]
    constraints:
      - "不能影响源库性能（要求延迟 < 100ms）"
    assumptions:
      - "数据日增 100 万订单"
      - "历史 3 年数据需保留"
```

## 4. 经验教训

### 踩坑 #1：业务方口头确认的"GMV"到底包不包含退款？

**场景**：上线后业务方反馈"GMV 与财务对不上"，检查发现 GMV 未排除退款。
**原因**：需求阶段业务方口头说"就是成交总额"，但"成交"在不同部门有不同理解。
**解决**：上线后补充退款过滤逻辑，与财务部门对齐口径。
**预防**：每个指标必须明确"计算公式 + 过滤条件 + 排除项"，并书面确认。

### 踩坑 #2：需求变更导致表结构大改

**场景**：开发到一半，业务方要求增加一个分析维度，原表无法支撑，需要重构。
**原因**：未识别"潜在需求"，仅做表面需求。
**解决**：增加维度列，补充历史数据回溯脚本。
**预防**：需求分析时多问一句"未来还可能加什么维度？"，预留字段和扩展点。

### 踩坑 #3：跨部门需求优先级冲突

**场景**：销售部要求日报早上 7 点出，财务部要求月报月底前出，时间冲突。
**原因**：未识别多方需求和依赖关系。
**解决**：分阶段交付，日报先做，月报后做。
**预防**：需求评审时邀请所有利益相关方，提前暴露冲突。

### 踩坑 #4：技术约束被业务方低估

**场景**：业务方要求"实时"出数据，但源库是 MySQL，无法支持。
**原因**：业务方不了解技术限制，未引入技术方参与。
**解决**：改为准实时（T+1 8 点），部分场景使用增量同步。
**预防**：需求评审必须有技术方在场，提前评估可行性。

## 5. 协作建议

### 5.1 与业务方协作

| 阶段 | 协作要点 |
|------|---------|
| 需求调研 | 访谈前准备问题清单，多问"为什么"和"还有什么" |
| 需求评审 | 邀请所有利益相关方，书面记录讨论结论 |
| 需求确认 | 关键指标必须签字确认，保留邮件/会议纪要 |
| 需求变更 | 任何变更走正式流程，评估影响后审批 |

### 5.2 与技术团队协作

| 场景 | 协作要点 |
|------|---------|
| 需求初稿 | 与架构师对齐技术可行性 |
| 需求定稿 | 与开发负责人评估工作量 |
| 需求变更 | 与测试负责人沟通测试范围影响 |
| 上线验收 | 与运维确认发布窗口和回滚方案 |

### 5.3 需求文档管理

- **统一格式**：使用本规范中的 YAML 模板
- **集中存放**：所有需求包存放在 `requirements/` 目录
- **版本控制**：使用 Git 管理变更历史
- **变更通知**：每次变更必须在群里公告，并@相关人
