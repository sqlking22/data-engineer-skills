一、数据仓库模型设计

1.1 数据分层模型

腾讯数据仓库采用标准的多层架构设计，主要包含以下分层：

┌─────────────────────────────────────────────────────────────┐
│                      APP/DM 应用层                            │
│  数据应用层、数据集市层，提供给数据产品和数据分析使用            │
└─────────────────────────────────────────────────────────────┘
                              ▲
                              │
┌─────────────────────────────────────────────────────────────┐
│                   DWS 汇总层（服务层）                         │
│  公共汇总粒度事实层，进行轻度汇总，基于DWD层整合汇总分析主题       │
└─────────────────────────────────────────────────────────────┘
                              ▲
                              │
┌─────────────────────────────────────────────────────────────┐
│                   DWM 中间层（可选）                          │
│  数据中间层，对DWD层数据进行轻度聚合，生成中间表               │
└─────────────────────────────────────────────────────────────┘
                              ▲
                              │
┌─────────────────────────────────────────────────────────────┐
│                   DWD 明细层                                 │
│  数据仓库明细层，保持与ODS层相同粒度，进行数据清洗和规范化       │
└─────────────────────────────────────────────────────────────┘
                              ▲
                              │
┌─────────────────────────────────────────────────────────────┐
│                   ODS 贴源层                                │
│  操作数据存储层，最接近数据源，原封不动接入原始数据             │
└─────────────────────────────────────────────────────────────┘

各层详细说明

分层 全称 中文名 功能说明
ODS Operational Data Store 操作数据存储层/贴源层 最接近数据源的一层，保持与源系统数据一致，不做数据清洗转换
DWD Data Warehouse Detail 数据仓库明细层 保持与ODS层相同数据粒度，提供数据质量保证，进行数据清洗、整合、规范化
DWM Data Warehouse Middle 数据仓库中间层 在DWD层基础上进行轻度聚合操作，生成中间表，提升公共指标复用性
DWS Data Warehouse Service 数据仓库服务层 公共汇总层，进行轻度汇总，粒度比明细数据稍粗，一般为宽表
DIM Dimension 维度层 存储维度信息和配置表，包含高基数维度（用户、商品资料）和低基数维度（枚举值配置）
DM/APP Data Market/Application 数据集市/应用层 提供给数据产品和数据分析使用的数据，包含报表数据等

1.2 数据分层边界

数据流向标准（不含维度）：ODS → DWD → DWS → DM
维度流向：DWD → DIM 或 ODS → DIM
禁止反向依赖

分层调用规范：

  1. DWA/DM应用层优先调用DWS层数据，不允许跨过DWS层从DWD层重复加工
  2. DWS应积极了解应用层数据需求，将公共数据沉淀后提供数据服务
  3. ODS层数据不能直接被应用层任务引用
  4. 从ODS到DWS层任务深度不宜过大（建议不超过10层）
  5. DWM汇总层优先调用DWD明细层，避免大量汇总数据直接从海量明细数据中计算
  6. 有针对性地建设DWM公共汇总层，避免应用层过度依赖DWD层明细数据

1.3 数据主题域

主题域是面向业务分析，将业务分析过程进行高度概括及抽象，是在较高层次上将企业信息系统中的数据综合、归类并进行分析利用的抽象。

常见主题域分类：

主题域 描述 示例内容
用户主题域 描述各类参与人在业务场景中的信息 用户资料、身份信息、人口统计、费用、账户信息
行为主题域 描述各类参与人的行为信息 UGC发表、评论、登录、下载、付费等行为
内容主题域 描述各类内容信息 文章、视频、音频等多媒体内容
产品主题域 描述产品相关信息 商品、服务、功能模块等
渠道主题域 描述渠道相关信息 推广渠道、销售渠道、合作伙伴等
交易主题域 描述交易相关信息 订单、支付、退款等

二、数据仓库规范定义

2.1 表命名规则

2.1.1 总体命名规范

命名公式：

[数据分层]_[BG]_[业务域]_[主题域]_[业务描述]_[刷新周期]_[存储策略]

组成部分说明：

组成部分 说明 可选值 备注
数据分层 表所在分层 ods/dwd/dws/dwm/dim/app/dm 必填
BG 事业群 WXG/PCG/IEG/CSIG/TEG/CDG 可选
业务域 业务线简称 如应用宝(yyb)、信息安全(infosec) 可选
主题域 业务过程抽象 user/ad/game等 可选
业务描述 业务过程提炼 见名知意 必填
刷新周期 h/d/w/m/q/y 小时/天/周/月/季/年 必填
存储策略 i/f 增量/全量 必填

命名示例：

dwd_pcg_yyb_user_info_df
├── dwd: 明细层
├── pcg: PCG事业群
├── yyb: 应用宝业务线
├── user: 用户主题域
├── info: 基础信息描述
├── d: 天级刷新
└── f: 全量存储

2.1.2 各分层命名细则

ODS层命名规范

格式： ods_[业务域]_[业务描述]_[加载方式]

加载方式后缀：

  • -S: 实时加载
  • -I: 增量加载（DI：天级增量，HI：小时级增量）
  • -A: 全量加载（DA：天级全量，HA：小时级全量）
  • -H: 历史表

命名示例：

表命名 说明
ods_tmall_mysql_order_info_di 天猫MySQL订单信息表，天级增量
ods_pcg_yyb_user_info_df 应用宝用户基础信息表，按天全量
ods_snap_stream_load Stream Load快照表

处理内容：

  • 源系统数据的采集和同步，保持与源系统数据一致
  • 实时接入数据需包含数据写入状态（新增、修改、删除）和实时写入时间
  • 快照表处理：
    • 数据量<100万：按天/周/月做全量快照表
    • 数据量>1000万：根据业务主键做拉链表
    • 数据量100万-1000万：根据业务需求决定
  • 补录表处理：需包含固定模板、适用范围、有效期、更新机制
DWD层命名规范

格式： dwd_[主题名]_[加工方式]

加工方式后缀：

  • _H: 按时加工
  • _D: 按日加工

命名示例：

表命名 说明
dwd_sales_di 销售明细表，按日加工
dwd_pcg_yyb_click_log_di 应用宝点击日志表，按天增量
dwd_wxg_game_gamecenter_click_di 微信游戏中心点击表，天级增量

处理内容：

  • 数据完整性保障（实体完整性、数据行完整性、字段完整性）
  • 数据清洗：对脏数据按规则进行清洗
  • 维度关联映射
  • 维度退化：减少事实表和维表的关联
  • 相同主题数据汇集，提高可用性
DWM层命名规范

格式： dwm_[主题名]_[功能描述]_[加工方式]

命名示例：

表命名 说明
dwm_wxg_game_behavior_gamecenter_click_di 微信游戏中心点击表，天级增量
dwm_teg_infosec_user_ugc_post_d 信安用户UGC发表行为，天增量

处理内容：

  • 对通用的核心维度进行聚合操作
  • 计算相应的统计指标
  • 提升公共指标的复用性，减少重复加工
DWS层命名规范

格式： dws_[主题名]_[功能描述] 或 dws_[主题内容]_[统计周期]

命名示例：

表命名 说明
dws_sales_order_analysis 销售订单分析表
dws_pcg_yyb_user_dau_di 用户日活相关汇总表，按天增量
dws_wxg_game_gamecenter_click_di 微信游戏中心点击表，天级增量
dws_load_d 导入相关主题表，按天统计

处理内容：

  • 不同实体间的关联和逻辑转换
  • 维度退化
  • 不同粒度的指标度量和轻度汇总
  • 覆盖80%的应用场景
  • 形成宽表，提供后续业务查询、OLAP分析、数据分发
DIM层命名规范

格式： dim_[维表类别] 或 dim_[主题域][维度类型][维度]

维表类别： 用户、日期、地址、标签等

命名示例：

表命名 说明
dim_user_info 用户维度表
dim_date 日期维度表
dim_city 城市维表，静态数据
dim_channel_df 渠道维表，按天全量
dim_doris_scd_load 导入维度，缓慢变化维

处理内容：

  • 维度的一致性和准确性
  • 数据行中为空维度的兼容处理
  • 缓慢变化维（SCD）：保留历史数据和版本，TTL为30天
  • 字段冗余设计，采用列存储方式
DM/APP层命名规范

格式： dm_[项目/分析域][主题内容][统计周期] 或 app_[应用系统标识]_[业务描述]_[刷新周期][存储策略]

命名示例：

表命名 说明
app_pcg_yyb_show_user_dau_di 用户日活报表，按天增量
dm_doris_load_d Doris导入相关分析，按天统计
app_wxg_game_open_social_di 微信游戏开放平台社交报表，天增量
app_teg_index_galilei_doc_profile_df 腾讯指数伽利略文章画像，天全量

处理内容：

  • 基于不同分析主题的宽表
  • 维度和指标的提取
  • 指标粒度一致性
  • 数据高度汇总
  • 保障维度完整性
TMP层命名规范

格式： tmp_[正式表名]_[时间戳(yyyyMMdd)]_[编号] 或 tmp_[用户][表内容][有效期]

命名示例：

表命名 说明
tmp_app_yyb_show_user_dau_di_20190501_001 对应表的临时表，20190501天001编号

处理内容：

  • ETL作业中的临时表，可临时创建和删除
  • 需设置确定的生命周期
  • 模型管理员根据有效期和用户确认清理计划

2.1.3 其他表类型命名规范

表类型 命名格式 说明

2.2 字段命名规范

2.2.1 基本原则

  • 字段名见名知意，统一标准，降低数据沟通成本

  • 字段与系统关键字冲突时加_col后缀

三、数据仓库开发规范

3.1 原则约定

3.1.1 数据复用，共享精神

  • 各业务优先使用公共数据中间层数据
  • 个性化指标可自行设计数据模型，统一命名

3.1.2 命名规范化，一致性

  • 采用统一命名规范，见名知意
  • 降低数据沟通成本及使用成本

3.2 数据层级调用规范（强校验）

  1. 各业务、应用优先使用DW公共数据中间层数据
  2. 已经存在中间层数据，不允许应用层跨过中间层从ODS重复加工数据
  3. 各业务、应用团队需积极配合公共数据中间层团队进行数据建设改造和迁移
  4. 公共数据中间层团队应积极了解应用层数据需求，将公用数据沉淀到公共层

3.3 数据脚本开发规范

3.3.1 脚本开发基本要求

  1. 原则上一个脚本产生一个表
  2. 原则上一个脚本命名与生成表命名一致
  3. 脚本统一采用Git管理
  4. 禁止使用SELECT *操作，所有操作必须明确指定列名

3.3.2 注释规范

  • 程序头注释：功能、人员、时间等信息
  • 代码段注释：每段代码前必须包含注释行，描述代码功能
  • 表注释：每个表需填写注释，描述表功能、使用说明
  • 字段注释：填写字段说明，枚举值字段需填写含义或维表

3.3.3 代码流程开发规范

┌─────────────────────────────────────┐
│           输入层（ODS/DWD）           │
└─────────────────────────────────────┘
                  ▼
┌─────────────────────────────────────┐
│       数据处理逻辑（清洗/转换）        │
│   - 数据清洗                        │
│   - 数据转换                        │
│   - 数据关联                        │
└─────────────────────────────────────┘
                  ▼
┌─────────────────────────────────────┐
│           输出层（目标表）            │
└─────────────────────────────────────┘

3.4 建表规范（强校验）

  1. 建表时遵守命名规范，优先建立分区表
  2. 禁止通过程序批量新建以时间戳为后缀的非分区表，需优化为分区表
  3. 每个表需要填写注释，描述表功能、使用说明
  4. 字段注释必须填写，禁止全空备注信息建表
  5. 一个计算刷新任务只允许一个输出表，特殊情况除外

3.5 计算时间窗口规范（强校验）

  1. 全量计算转日增量
  2. 对于跨多日期窗口计算任务（如对ODS近7天数据进行查询及汇总计算）：
    • 单分区超过5G：需拆分为每日增量进行计算落地中间数据
    • 任务执行超过1小时：需拆分为每日增量进行计算落地中间数据
  3. 再基于中间数据进行进一步汇总计算

3.6 SQL编码规范

3.6.1 总原则

  • 代码功能完整、健壮
  • 代码行清晰、整齐，层次分明，结构化强
  • 代码编写充分考虑执行速度最优的原则
  • SQL关键字、保留字使用大写（SELECT、FROM、WHERE、AND、OR等）
  • 字段名、别名等使用小写
  • 四个空格为一个缩进量，所有缩进为一个缩进量的整数倍
  • 对应的括号在同一列位置上

3.6.2 SELECT子句格式规范

-- 字段排列规范
SELECT
    userId        AS userId        -- 用户ID
    , gender      AS gender        -- 性别
    , city        AS cityName      -- 城市名称
    , prov        AS provName      -- 省份名称
FROM default.table1
WHERE 1=1
    AND ds = '%yyyyMMdd%'          -- 时间分区

规范要点：

  • SELECT语句选择的字段按每一行一个字段编排
  • SELECT单字后一个缩进量直接跟首个选择字段
  • 其他字段前导两个缩进量
  • 逗号分隔符紧跟在第二个字段前面
  • AS语句与相应字段在同一行

3.6.3 CASE语句格式规范

SELECT
    userId        AS userId
    , (CASE WHEN gender = 0 THEN '男'
            WHEN gender = 1 THEN '女'
            WHEN gender > 1 THEN '未知'
            ELSE '未知' END) AS gender_cn
FROM default.table1
WHERE 1=1
    AND ds = '%yyyyMMdd%'

规范要点：

  • WHERE子句在CASE语句同一行并缩进一个缩进量
  • 每个WHEN子句一行编写
  • CASE语句必须包含ELSE子句
  • ELSE子句与WHERE子句对齐

3.6.4 子嵌套语句格式规范

SELECT
    userId
    , gender_cn
FROM (
    SELECT
        userId        AS userId
        , (CASE
            WHEN gender = 0 THEN '男'
            WHEN gender = 1 THEN '女'
            WHEN gender > 1 THEN '未知'
           ELSE '未知'
           END) AS gender_cn
    FROM default.table1
    WHERE ds = '%yyyyMMdd%'
) a
WHERE 1 = 1
    AND a.gender_cn = '女'

规范要点：

  • 子嵌套语句与父语句整体缩进一个缩进量
  • 括号在同一列位置上

3.6.5 INSERT子句格式规范

-- INSERT子句写在同一行，不需要换行
INSERT OVERWRITE TABLE demo_table PARTITION(ds = '%yyyyMMdd%')

3.6.6 运算符间隔规范

  • 算数运算符、逻辑运算符前后保留一个空格
  • 除非超过每行80字符长度限制，否则写在同一行

四、公共开发规范

4.1 数据类型规范

在保障数据不失真，且不增加存储复杂度和计算量的情况下，尽量减少数据类型数量。

Apache Doris数据类型规范：

数据类型 说明 示例
BIGINT ID类字段 user_id BIGINT
INT 标签枚举 status INT
STRING 字符串 user_name STRING
STRING 状态描述 status_desc STRING
DATE 日期 order_date DATE (yyyy-MM-dd)
DATETIME 日期时间 create_time DATETIME (yyyy-MM-dd HH:mm:ss.SSSSSS)
DECIMAL 业务数额类 amount DECIMAL(28,6)

4.2 NULL字段处理规范

数据类型 默认值 说明
int -999 维度字段NULL值处理
bigint -999999 维度字段NULL值处理
decimal 0 指标字段NULL值处理

对于维度字段需设置为-1；对于指标字段需设置为0

4.3 数据冗余规范

宽表冗余字段需确保以下原则：

  • 冗余字段使用频率高（下游3个或以上使用）
  • 冗余字段引入不应造成数据产生过多延后
  • 冗余字段与已有字段的重复率不应超过60%
  • 如需要可选择join或原表拓展

4.4 公共字段规范

所有数仓分层中的字段均为小写，且不可出现中文。

公共字段信息：

字段名 类型 说明
id BIGINT 主键ID
create_time DATETIME 创建时间
update_time DATETIME 更新时间
creator STRING 创建人
updater STRING 更新人
is_deleted TINYINT 是否删除(0否1是)
ds STRING 分区字段(yyyyMMdd)

4.5 数据表处理规范

4.5.1 增量表

  • 依据时间和其他标签粒度做对应分区或多层分区
  • 源表必须包含可增量属性字段，确保数据完整性
  • 记录每次增加的量，不是总量
  • 只报变化量，无变化不用报
  • 每天一个分区

4.5.2 全量表

  • 每次写入的数据都是最新的
  • 每次写入的数据都是完整的全量数据
  • 有无变化都要报
  • 只有一个分区

4.5.3 快照表

  • 按日分区，记录截止数据日期的全量数据
  • 有无变化都要报
  • 每次上报所有数据（变化的+没有变化的）
  • 一天一个分区

4.5.4 拉链表

  • 记录一个事物从开始到当前状态的所有变化信息
  • 每次上报的是历史记录的最终状态
  • 记录当前时刻的历史总量
  • 当前记录存的是当前时间之前所有历史记录的最后变化量
  • 只有一个分区

拉链表设计示例：

字段名 说明
id 主键
start_date 开始生效日期
end_date 结束生效日期
is_current 是否当前记录

4.6 事实表划分规范

在维度建模中，按粒度划分，数据表分为维度表和事实表，事实表包含三种：

事实表类型 说明 特点
事务型事实表 记录事务层面的事实，保存最为原子的数据 数据在事务发生后发生，粒度为每一行数据
周期快照型事实表 有规律的、可预见的时间间隔的业务累计数据 按天、周、月等做业务统计度量
累计快照型事实表 表述业务多个阶段的开始和结束过程 有多个时间字段，时间不可预测，随阶段变化记录也变化
