# 数据仓库规范体系

> 本文档是数据团队的数仓建模与开发规范，作为团队数仓建设的**唯一执行标准**。
> 基于业界通用的数仓方法论骨架（参考腾讯公开资料），结合实际技术栈与制造业 + 电商业务特点裁剪适配而成。

## 文档说明

**适用技术栈**：

* **AnalyticDB MySQL（ADB）**：数仓底座，承载 OLAP 数仓分析
* **MaxCompute**：大数据离线计算，承载海量数据处理

**业务范围**：PCB、PCBA、钢网、3D打印、元器件、CNC、FA、治具、软件服务、钣金、电热膜、手板复模、纸盒（国内 + 海外）。

**适用判断**：海量离线处理 → MaxCompute；OLAP 数仓分析 → ADB MySQL。

**方法论来源**（参考，非执行依据）：

* 腾讯云开发者社区公开数仓规范资料（命名规范、分层模型、开发规范）

> 执行以本文档为准。与本文档冲突的任何历史约定，以本文档为优先。

## 一、数据仓库模型设计

### 1.1 数据分层模型

数据仓库采用标准多层架构：

```
┌─────────────────────────────────────────────────────────────┐
│                      ADS 应用层                              │
│  面向数据产品、报表、数据大屏，高度汇总                         │
└─────────────────────────────────────────────────────────────┘
                              ▲
                              │
┌─────────────────────────────────────────────────────────────┐
│                      DWS 汇总层                              │
│  公共汇总层，轻度汇总，宽表，覆盖公共分析场景                    │
└─────────────────────────────────────────────────────────────┘
                              ▲
                              │
┌─────────────────────────────────────────────────────────────┐
│                      DWD 明细层                              │
│  保持 ODS 粒度，数据清洗、整合、规范化                          │
└─────────────────────────────────────────────────────────────┘
                              ▲
                              │
┌─────────────────────────────────────────────────────────────┐
│                      ODS 贴源层                              │
│  原样接入源系统数据，与源系统保持一致                           │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│                      DIM 维度层                              │
│  维度信息与配置表，横向贯穿各层（ODS/DWD → DIM）                │
└─────────────────────────────────────────────────────────────┘
```

#### 各层详细说明

| 分层 | 全称 | 功能说明 |
| --- | --- | --- |
| ODS | Operational Data Store | 贴源层，最接近数据源，与源系统数据一致，不做清洗转换 |
| DWD | Data Warehouse Detail | 明细层，保持 ODS 粒度，进行数据清洗、整合、规范化、维度退化 |
| DWS | Data Warehouse Service | 汇总层，轻度汇总，宽表，覆盖公共分析场景，提升公共指标复用性 |
| ADS | Application Data Service | 应用层，面向报表/数据产品/大屏，高度汇总 |
| DIM | Dimension | 维度层，存储维度信息与配置表，SCD Type 2 保留历史 |

> **说明**：**不单独设 DWM 中间层**——需要轻度聚合的公共逻辑直接沉淀到 DWS。应用层统一为 **ADS**，不再区分 DM / APP。

### 1.2 数据分层边界

```
数据流向（单向）：ODS → DWD → DWS → ADS
维度流向：ODS/DWD → DIM
禁止反向依赖
```

**分层调用规范：**

1. ADS 优先调用 DWS，不允许跨过 DWS 从 DWD 重复加工
2. DWS 应积极了解应用层需求，将公共数据沉淀后提供服务
3. ODS 不允许被应用层直接引用
4. ODS 到 DWS 任务深度不宜过大（建议不超过 10 层）
5. 需要轻度聚合时优先沉淀到 DWS，避免 ADS 过度依赖 DWD 明细

### 1.3 数据主题域

面向 **制造 + 电商**业务，主题域划分如下：

| 主题域 | 简写 | 说明 | 示例内容 |
| --- | --- | --- | --- |
| 客户 | customer | 客户/会员信息 | 客户资料、画像、等级 |
| 订单交易 | trade | 交易过程 | 订单、支付、退款 |
| 生产制造 | production | 生产过程 | PCB/PCBA 工序、生产工单、工艺 |
| 商品物料 | product | 商品与物料 | 商品、元器件、BOM |
| 物流交付 | logistics | 交付过程 | 发货、物流轨迹、签收 |
| 质量 | quality | 质量信息 | 质检、不良品、客诉 |
| 营销 | marketing | 营销活动 | 活动、渠道、推广 |

## 二、数据仓库规范定义

### 2.1 表命名规则

#### 2.1.1 总体命名规范

**命名公式（国内/通用）：**

```
[层]_[业务域]_[主题域]_[业务描述]_[刷新周期]_[存储策略]
```

**命名公式（海外）：** 在「业务描述」与「刷新周期」之间插入 `overseas` 标记：

```
[层]_[业务域]_[主题域]_[业务描述]_overseas_[刷新周期]_[存储策略]
```

**组成部分说明：**

| 组成部分 | 必填 | 说明 | 可选值/示例 |
| --- | --- | --- | --- |
| 层 | 是 | 表所在分层 | ods / dwd / dws / ads / dim |
| 业务域 | 是 | 业务线简写（见附录1） | pcb / pcba / component … |
| 主题域 | 否 | 主题域简写（见 1.3） | trade / production / product … |
| 业务描述 | 是 | 业务过程提炼，见名知意 | order_detail / sales_report |
| overseas | 否 | 海外表标记（仅海外表） | overseas |
| 刷新周期 | 是 | h/d/w/m/q/y | d |
| 存储策略 | 是 | i/f（增量/全量） | i |

**命名示例：**

```
dwd_pcb_trade_order_detail_di
├── dwd              明细层
├── pcb              PCB 业务域
├── trade            订单交易主题域
├── order_detail     订单明细（业务描述）
├── d                天级刷新
└── i                增量存储

dwd_pcb_trade_order_detail_overseas_di   （海外版）

ods_pcb_order_info_di   （主题域省略，贴源层常见）
```

#### 2.1.2 各分层命名细则

##### ODS 层命名规范

**格式：** `ods_[源业务库名简称]_[源表名]_[刷新周期]_[存储策略]`（主题域通常省略；外贸表后缀加 `_overseas`）

**命名示例：**

| 表命名 | 说明 |
| --- | --- |
| `ods_pcb_order_info_di` | PCB 订单信息表，天级增量 |
| `ods_component_stock_df` | 元器件库存表，天级全量 |

**处理内容：**

* 源系统数据的采集和同步，保持与源系统数据一致
* 实时接入数据需包含写入状态（新增/修改/删除）和实时写入时间
* 快照策略按数据量定：
  + 数据量 < 100 万：按天/周/月做全量快照表
  + 数据量 > 1000 万：根据业务主键做拉链表
  + 100 万–1000 万：根据业务需求决定

##### DWD 层命名规范

**格式：** `dwd_[业务域]_[主题域]_[业务描述]_[刷新周期]_[存储策略]`

**命名示例：**

| 表命名 | 说明 |
| --- | --- |
| `dwd_pcb_trade_order_detail_di` | PCB 订单明细，天级增量 |
| `dwd_component_product_stock_df` | 元器件商品库存，天级全量 |

**处理内容：**

* 数据完整性保障（实体完整性、数据行完整性、字段完整性）
* 数据清洗、维度关联映射、维度退化
* 相同主题数据汇集，提高可用性

##### DWS 层命名规范

**格式：** `dws_[业务域]_[主题域]_[业务描述]_[统计周期]_[存储策略]`（统计周期常用时间维度缩写，见 2.2.5）

**命名示例：**

| 表命名 | 说明 |
| --- | --- |
| `dws_pcb_trade_order_amt_1d_df` | PCB 订单金额，最近1天汇总，全量 |
| `dws_pcb_customer_active_1m_df` | PCB 活跃客户，最近30天汇总，全量 |

**处理内容：**

* 不同粒度的指标度量和轻度汇总
* 维度退化，形成宽表
* 覆盖公共分析场景，提供后续查询、OLAP 分析、数据分发

##### DIM 层命名规范

**格式：** `dim_[业务域]_[业务描述]_[存储策略]`

**命名示例：**

| 表命名 | 说明 |
| --- | --- |
| `dim_pcb_customer_df` | PCB 客户维度表，天级全量 |
| `dim_component_product_df` | 元器件商品维度表，天级全量 |
| `dim_date` | 日期维度表（通用，跨业务域） |

**处理内容：**

* 维度一致性和准确性
* 空维度的兼容处理
* 缓慢变化维（SCD Type 2）：保留历史
* 字段冗余设计，采用列存储

##### ADS 层命名规范

**格式：** `ads_[业务域]_[主题域]_[业务描述]_[刷新周期]_[存储策略]`

**命名示例：**

| 表命名 | 说明 |
| --- | --- |
| `ads_pcb_trade_sales_report_df` | PCB 销售报表，天级全量 |
| `ads_pcb_customer_dashboard_overseas_df` | PCB 客户大盘（海外），天级全量 |

**处理内容：**

* 基于分析主题的宽表，高度汇总
* 维度��指标的提取，指标粒度一致性
* 保障维度完整性

##### TMP / 中间表命名规范

**格式：** `tmp_[正式表名]_[yyyyMMdd]_[编号]`；中间表 `mid_[表名]_[序号]`

| 表命名 | 说明 |
| --- | --- |
| `tmp_dwd_pcb_trade_order_detail_di_20260617_001` | 对应表的临时表 |

**处理内容：** ETL 中的临时/中间数据，须设置确定的生命周期，定期清理。

#### 2.1.3 其他表类型命名规范

| 表类型 | 命名格式 | 说明 |
| --- | --- | --- |
| 视图 | `[层]_v_[主题名]_[功能描述]` | 如 `dws_v_trade_order` |
| 手工表 | `[层]_[业务域]_manual_[描述]` | 手工维护的表 |
| 中间表 | `mid_[table_name]_[0~9]` | Job 中临时存储的中间数据 |
| 临时表 | `tmp_xxx` | 临时测试使用，可随时删除 |

> **关于事实表前缀**：**不使用 `fct_` / `fact_` 等前缀**标记事实表。除 `dim_` 维度表外，其余表（DWD/DWS/ADS 中的明细、汇总、宽表）均按事实表对待。

### 2.2 字段命名规范

#### 2.2.1 基本原则

* 字段名见名知意，统一标准，降低沟通成本
* 英文名尽量使用全称，单词间用下划线分隔
* 字段与系统关键字冲突时加 `_col` 后缀
* **所有字段小写，不可出现中文**

#### 2.2.2 标准维度字段

| 维度类型 | 字段 | 命名 | 格式 | 示例 |
| --- | --- | --- | --- | --- |
| 时间类 | 统计日期 | stat\_date | YYYY-MM-DD | 2026-06-17 |
| 时间类 | 统计小时 | stat\_hour | HH | 22 |
| 账号类 | 客户ID | customer\_id | - | - |
| 账号类 | 用户ID | user\_id | - | - |
| 地点类 | 城市编码 | city\_id | - | - |
| 渠道类 | 渠道编码 | channel\_id | - | - |
| 应用类 | 应用编码 | app\_id | - | - |

#### 2.2.3 属性字段命名规范

| 字段类型 | 格式 | 说明 | 示例 |
| --- | --- | --- | --- |
| 属性字段 | `[通用英文单词]` | 文本字段，不加前后缀 | city\_name, address |
| 指标字段 | `[修饰词]_[原子词]_[时间修饰]` | 基础指标命名 | pcb\_pay\_ord\_amt\_1w |
| 计数字段 | `[计数主体]_cnt` | 件数、用户数等整型 | order\_cnt, user\_cnt |
| 比例字段 | `[计数主体]_rate` | 占比、百分率 | pay\_rate |
| 费用字段 | `[计数主体]_amt` | 费用、收入 | pay\_amt |
| 标识字段 | `is_[标识主体]` | 取值为 Y/N 或 0/1 | is\_active, is\_vip |
| 时间字段 | `[业务主体]_time` | YYYY-MM-DD HH:Mi:SS | order\_time |
| 日期字段 | `[业务主体]_date` | YYYY-MM-DD | order\_date |

**指标字段命名示例：**

```
最近七天 PCB 支付金额
├── 修饰词: pcb（PCB 业务域）
├── 原子词: pay_ord_amt（支付订单金额）
└── 时间修饰: _1w（最近7天）
结果: pcb_pay_ord_amt_1w
```

#### 2.2.4 分区字段规范

**分区字段统一使用 `dt`**（ADB 与 MaxCompute 保持一致）。

| 分区类型 | 字段名 | 格式 | 备注 |
| --- | --- | --- | --- |
| 日分区（默认） | dt | yyyyMMdd 或 yyyy-MM-dd | 默认业务运行日期 |
| 小时分区 | hh | 00..23 | - |
| 业务分区 | [自定义] | - | 如 channel 等业务维度 |

> 分区深度不建议超过 3 层。多级分区（如月 + 日）的具体命名在表设计时确定。

#### 2.2.5 时间维度规范（常用集）

| 中文名 | 缩写 | 描述 |
| --- | --- | --- |
| 最近一天 | \_1d | 最近1天 |
| 最近七天 | \_7d | 最近7天 |
| 最近30天 | \_30d | 最近30天 |
| 月初至今 | \_mtd | 自然月初截止当日 |
| 季初至今 | \_qtd | 自然季初截止当日 |
| 年初至今 | \_ytd | 自然年初截止当日 |
| 自然月 | \_cm | 自然月 |
| 自然季 | \_cq | 自然季度 |
| 自然年 | \_cy | 自然年 |

> 以上为常用集。其余扩展（自然周、财年、半财年等）按需补充，不在默认集中。

## 三、数据仓库开发规范

### 3.1 原则约定

* **数据复用，共享精神**：各业务优先使用公共中间层数据；个性化指标可自行设计并统一命名
* **命名规范化、一致性**：统一命名规范，见名知意，降低沟通与使用成本

### 3.2 数据层级调用规范（强校验）

1. 各业务、应用优先使用 DW 公共中间层数据
2. 已存在中间层数据的，不允许应用层跨过中间层从 ODS 重复加工
3. 各业务、应用团队需积极配合公共中间层的数据建设改造和迁移
4. 公共中间层团队应积极了解应用层需求，将公共数据沉淀到公共层

### 3.3 数据脚本开发规范

**脚本开发基本要求：**

1. 原则上一个脚本产生一个表，脚本命名与生成表命名一致
2. 脚本统一采用 Git 管理
3. 禁止使用 `SELECT *`，所有操作必须明确指定列名

**注释规范：**

* **程序头注释**：功能、人员、时间等信息
* **代码段注释**：每段代码前必须包含注释，描述功能
* **表注释**：每个表需填写注释，描述表功能、使用说明
* **字段注释**：填写字段说明，枚举值字段需填写含义或维表

### 3.4 建表规范（强校验）

1. 遵守命名规范，优先建立分区表
2. 禁止批量新建以时间戳为后缀的非分区表，须优化为分区表
3. 每个表需填写注释，描述表功能、使用说明
4. 字段注释必须填写，禁止全空备注建表
5. 一个计算刷新任务只允许一个输出表（特殊情况除外）

### 3.5 计算时间窗口规范（强校验）

1. 全量计算转日增量
2. 跨多日期窗口计算任务（如对 ODS 近 7 天数据查询汇总）：
   * 单分区超过 5G：需拆分为每日增量落地中间数据
   * 任务执行超过 1 小时：需拆分为每日增量落地中间数据
3. 再基于中间数据进一步汇总

### 3.6 SQL 编码规范

> SQL 编码规范（关键字大小写、缩进、SELECT / CASE / INSERT 格式、运算符间隔、ADB 与 MaxCompute 方言写法等）**单独维护**，详见 **《SQL 编码规范》**。
>
> 本规范不再重复 SQL 编码细则，以避免双份标准不一致。一切 SQL 编码以《SQL 编码规范》为准。

## 四、公共开发规范

### 4.1 数据类型规范

在保障数据不失真、且不增加存储复杂度和计算量的前提下，尽量减少数据类型数量。按用途选型，双库类型对照如下：

| 用途 | ADB MySQL | MaxCompute | 示例 |
| --- | --- | --- | --- |
| ID / 主键 / 外键 | BIGINT | BIGINT | `order_id BIGINT` |
| 枚举 / 状态 | INT / TINYINT | BIGINT | `order_status INT` |
| 短文本 | VARCHAR(n) | STRING | `customer_name VARCHAR(100)` |
| 长文本 | VARCHAR(n) | STRING | `remark VARCHAR(2000)` |
| 日期 | DATE | DATE | `order_date DATE` |
| 日期时间 | DATETIME | DATETIME | `create_time DATETIME` |
| 金额 / 数额 | DECIMAL(p,s) | DECIMAL(p,s) | `amount DECIMAL(18,2)` |
| 布尔 | TINYINT(0/1) | BOOLEAN / BIGINT | `is_deleted TINYINT` |

**要点：**

* ADB **不支持 UNSIGNED**；金额精度按业务定（如 `DECIMAL(18,2)`），不固定为 `(28,6)`
* ID 类字段统一 BIGINT；金额类禁止用 DOUBLE，必须用 DECIMAL

### 4.2 NULL 字段处理规范

**不使用 `-999` / `-999999` 等哨兵值**，统一用函数兜底：

| 场景 | 处理方式 |
| --- | --- |
| 维度字段为空 | `COALESCE(col, 默认值)` |
| 指标字段为空 | `COALESCE(col, 0)` |
| ADB 备选 | `IFNULL(a, b)` |
| MaxCompute 备选 | `NVL(a, b)` |

> `COALESCE` 为双库通用首选。

### 4.3 数据冗余规范

宽表冗余字段须满足：

* 冗余字段使用频率高（下游 3 个或以上使用）
* 冗余字段引入不应造成数据过大延后
* 冗余字段与已有字段的重复率不应超过 60%
* 如需要可选择 join 或原表拓展

### 4.4 公共字段规范

所有数仓分层中的字段均为小写，且不可出现中文。

**公共字段信息：**

| 字段名 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGINT | 主键 ID |
| create\_time | DATETIME | 创建时间 |
| update\_time | DATETIME | 更新时间 |
| creator | VARCHAR | 创建人 |
| updater | VARCHAR | 更新人 |
| is\_deleted | TINYINT | 是否删除（0否1是） |
| dt | STRING / DATE | 分区字段 |

### 4.5 数据表处理规范

#### 4.5.1 增量表

* 依据时间和其他标签粒度做分区
* 源表必须包含可增量属性字段，确保数据完整性
* 只记录每次增加的变化量，无变化不报
* 每天一个分区

#### 4.5.2 全量表

* 每次写入的数据都是最新的、完整的全量数据
* 有无变化都要报
* 只有一个分区

#### 4.5.3 快照表

* 按日分区，记录截止数据日期的全量数据
* 有无变化都要报，每次上报所有数据
* 一天一个分区

#### 4.5.4 拉链表

记录一个事物从开始到当前状态的所有变化信息。

* 每次上报的是历史记录的最终状态
* 记录当前时刻的历史总量
* 只有一个分区

**拉链表设计示例：**

| 字段名 | 说明 |
| --- | --- |
| id | 主键 |
| start\_date | 开始生效日期 |
| end\_date | 结束生效日期（当前记录用远期哨兵日期，如 `9999-12-31`） |
| is\_current | 是否当前记录 |

### 4.6 事实表划分规范

按粒度划分，事实表包含三种类型：

| 事实表类型 | 说明 | 特点 |
| --- | --- | --- |
| 事务型事实表 | 记录事务层面的事实，保存最原子数据 | 粒度为每一行业务事件 |
| 周期快照型事实表 | 有规律时间间隔的业务累计数据 | 按天/周/月做统计度量 |
| 累计快照型事实表 | 表述业务多个阶段的开始和结束过程 | 多个时间字段，如订单创建→生产→发货→签收 |

### 附录4：ADB MySQL 物理设计强约束（建 DDL 前必读）

1. **分布键**：`DISTRIBUTED BY HASH(col)`，必须选高基数字段
2. **分区**：`PARTITION BY VALUE(col) LIFECYCLE n`，保留 n 个分区；分区字段统一 `dt`
3. **主键**：`PRIMARY KEY` 必须包含分布键 + 分区键；ADB 无独立 `UNIQUE KEY`，靠主键保证唯一
4. **聚集索引**：`CLUSTERED KEY(col)`，每个表仅 1 个，决定分区内的物理排序
5. **索引必须内联**在建表语句中，不支持独立的 `CREATE INDEX`
6. 普通索引单列，不支持多列复合索引 `INDEX(a,b)`
7. 不支持 `UNSIGNED`
8. `AUTO_INCREMENT` 仅限 BIGINT，值非顺序递增

**ADB 建表示例：**

```sql
CREATE TABLE dwd_pcb_trade_order_detail_di (
    order_id      BIGINT        NOT NULL COMMENT '订单ID',
    customer_id   BIGINT        NOT NULL COMMENT '客户ID',
    order_time    DATETIME      NOT NULL COMMENT '订单时间',
    order_amt     DECIMAL(18,2)          COMMENT '订单金额',
    dt            DATE          NOT NULL COMMENT '日分区',
    PRIMARY KEY (order_id, dt)            -- 主键含分布键 + 分区键
)
DISTRIBUTED BY HASH(order_id)             -- 高基数分布键
PARTITION BY VALUE(DATE_FORMAT(dt, '%Y%m%d')) LIFECYCLE 365
COMMENT 'PCB订单交易明细表（日增量）';
```

### 附录5：ADB MySQL vs MaxCompute 方言速查

| 维度 | AnalyticDB MySQL | MaxCompute |
| --- | --- | --- |
| 分布键 | `DISTRIBUTED BY HASH(col)`（高基数列） | 自动分布 |
| 分区 | `PARTITION BY VALUE(col) LIFECYCLE n` | 分区字段（dt）+ `LIFECYCLE n`（天数） |
| 主键 | `PRIMARY KEY`（含分布键+分区键） | 无主键约束 |
| 聚集索引 | `CLUSTERED KEY`（每表1个） | 不支持 |
| 条件函数 | `IF` / `CASE WHEN` | `IF` / `CASE WHEN`（多分支用 CASE WHEN） |
| 当前日期 | `CURDATE()` / `NOW()` | `GETDATE()` |
| 日期加减 | `DATE_ADD(d, INTERVAL n DAY)` | `DATEADD(d, n, 'dd')` |
| 分组连接 | `GROUP_CONCAT(col)` | `WM_CONCAT(col)` |
| NULL 处理 | `COALESCE(a, b)` / `IFNULL` | `COALESCE(a, b)` / `NVL(a, b)` |
| 大表 JOIN | 分布键对齐 + `/*+ BROADCAST_JOIN(t) */` | `/*+ MAPJOIN(t) */`（小表入内存） |
| 分区裁剪 | WHERE 必须带分区列 | WHERE 必须带分区字段 |

> 适用判断：海量离线处理 → MaxCompute；OLAP 数仓分析 → ADB MySQL。
