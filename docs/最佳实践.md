## 需求分析最佳实践

> 📖 **完整最佳实践指南（含反模式、模板、经验教训）**：[requirement-analyst/references/best-practices.md](../requirement-analyst/references/best-practices.md)

### 1. 提供充分的业务上下文

```bash
# ✅ 好的需求描述
/requirement-analyst 分析电商销售分析需求：
- 业务目标：统计各区域销售额、订单量、客单价
- 数据源：订单表（日增10万条）、用户表（100万用户）
- 分析维度：日期、区域、品类、用户等级
- 数据库：MaxCompute数仓
- 时效要求：T+1
- 数据保留：3年

# ❌ 不好的需求描述
/requirement-analyst 分析销售数据
```

### 2. 明确关键实体和指标

需求描述应包含：

| 要素 | 说明 | 示例 |
|------|------|------|
| 实体 | 核心业务对象 | 订单、用户、商品 |
| 指标 | 量化度量 | 销售额、订单量、转化率 |
| 维度 | 分析角度 | 日期、区域、品类 |
| 约束 | 业务规则 | 订单状态只能是已完成 |

### 3. 非功能性需求

不要忽略：
- 数据时效（T+1 / 实时）
- 数据量级（日增量 / 总量）
- 数据质量要求（准确率、完整性）
- 合规要求（敏感数据脱敏）

## 数据建模最佳实践

> 📖 **完整最佳实践指南（含 OneData vs Kimball、命名反例、SQL 示例、踩坑教训）**：[modeling-assistant/references/best-practices.md](../modeling-assistant/references/best-practices.md)

### 1. 事实表设计原则

```yaml
# 粒度原则
- 事实表粒度应是最细的业务级别
- 例如：订单项级别 > 订单级别

# 度量选择
- 选择可加性度量（如销售额）
- 避免半可加性度量（如账户余额）
- 为不可加度量提供计算说明（如比率）

# 示例
fct_order_items:
  grain: "订单项级别"  # 最细粒度
  measures:
    - name: "quantity"
      type: "additive"  # 可加
    - name: "amount"
      type: "additive"  # 可加
    - name: "unit_price"
      type: "non-additive"  # 不可加，需说明计算方式
```

### 2. 维度表设计原则

```yaml
# 维度属性丰富
dim_user:
  attributes:
    - user_id       # 自然键
    - username      # 描述性属性
    - city          # 地理属性
    - user_level    # 分类属性
    - register_date # 时间属性

# SCD策略选择
- Type 1: 覆盖旧值（不需要历史）
- Type 2: 新增记录（需要追踪历史）
- Type 3: 新增字段（需要有限历史）
```

### 3. 命名规范

```bash
# 表命名
事实表: fct_{业务主题}
维度表: dim_{维度名称}
聚合表: agg_{聚合内容}
报表表: rpt_{报表名称}

# 字段命名
主键: {表名}_id 或 {表名}_sk
外键: {关联表}_id 或 {关联表}_sk
时间: {动作}_time 或 {动作}_date
金额: {类型}_amount
数量: {类型}_count 或 {类型}_quantity
```

### 4. 不同数据库建模差异

| 数据库 | 分区策略 | 分布策略 | 索引策略 |
|--------|---------|---------|---------|
| MaxCompute | 分区字段定义 | 自动分布 | 无 |
| ADB MySQL | PARTITION BY VALUE | DISTRIBUTED BY HASH | 聚簇索引 |

## SQL开发最佳实践

> 📖 **完整最佳实践指南（含 SQL 正反例、性能调优）**：[sql-assistant/references/best-practices.md](../sql-assistant/references/best-practices.md)

### 1. 数据库选择指南

| 场景 | 推荐数据库 | 原因 |
|------|-----------|------|
| 海量离线处理 | MaxCompute | 成本低、稳定性高 |
| OLAP分析 | ADB MySQL | 兼容MySQL、易上手 |

### 2. 性能优化

#### MaxCompute

```sql
-- ✅ 使用分区裁剪
SELECT * FROM orders
WHERE pt = '202401'  -- 分区条件
  AND dt BETWEEN '01' AND '31';

-- ✅ 使用MAPJOIN优化小表JOIN
SELECT /*+ MAPJOIN(dim_user) */ *
FROM orders o
JOIN dim_user u ON o.user_id = u.user_id;

-- ❌ 避免全表扫描
SELECT * FROM orders;  -- 没有分区条件
```

#### ADB MySQL

```sql
-- ✅ 使用分区裁剪
SELECT * FROM orders
WHERE DATE_FORMAT(order_time, '%Y%m') = '202401';

-- ✅ 使用聚簇索引
SELECT * FROM orders
WHERE user_id = 1001
  AND order_time >= '2024-01-01';

-- ❌ 避免不带分区条件的查询
SELECT * FROM orders WHERE user_id = 1001;
```

### 3. 代码规范

```sql
-- ✅ 推荐格式
SELECT
    order_id,
    user_id,
    SUM(amount) AS total_amount
FROM orders
WHERE order_time >= '2024-01-01'
GROUP BY order_id, user_id
ORDER BY total_amount DESC
LIMIT 100;

-- ❌ 不推荐格式
select order_id,user_id,sum(amount) as total_amount from orders where order_time>='2024-01-01' group by order_id,user_id order by total_amount desc limit 100;
```

## 数据质量最佳实践

> 📖 **完整最佳实践指南（含规则反模式、阈值设置、踩坑教训）**：[dq-assistant/references/best-practices.md](../dq-assistant/references/best-practices.md)

### 1. 质量规则层次

```yaml
# Level 1: 基础规则（必须）
- 字段非空检查
- 主键唯一性检查
- 数据类型检查

# Level 2: 业务规则（重要）
- 枚举值检查
- 范围检查
- 格式检查

# Level 3: 自定义规则（可选）
- 业务逻辑检查
- 跨表一致性检查
- 历史趋势检查
```

### 2. 规则优先级设置

```yaml
rules:
  - name: "order_id_not_null"
    severity: "error"    # 必须修复
    
  - name: "amount_range"
    severity: "warning"  # 建议修复
    
  - name: "format_check"
    severity: "info"     # 提醒即可
```

### 3. 质量阈值设置

| 数据类型 | 推荐阈值 | 说明 |
|---------|---------|------|
| 核心业务数据 | 100% | 完全准确 |
| 财务数据 | 99.99% | 几乎完全准确 |
| 用户行为数据 | 99% | 允许少量丢失 |
| 日志数据 | 95% | 可接受一定误差 |

## 性能优化最佳实践

### 1. 数据库特定优化

#### MaxCompute

```sql
-- 设置并行度
SET odps.sql.parallel.factor=10;

-- 设置内存
SET odps.sql.reducer.instances=100;

-- 合并小文件
SET odps.sql.merge.smallfile.enabled=true;
```

#### ADB MySQL

```sql
-- 使用聚簇索引优化查询
-- ⚠️ ADB不支持独立CREATE CLUSTERED INDEX，必须内联定义或用ALTER TABLE：
--   建表时内联：CLUSTERED KEY idx_cluster(user_id, order_time)
--   或表已存在：ALTER TABLE orders ADD CLUSTERED KEY idx_cluster(user_id, order_time);

-- 使用近似计算加速
SELECT APPROX_COUNT_DISTINCT(user_id) AS uv
FROM orders;
```

### 2. 查询优化技巧

```sql
-- ✅ 使用CTE提高可读性
WITH daily_orders AS (
    SELECT
        DATE(order_time) AS order_date,
        COUNT(*) AS order_count
    FROM orders
    WHERE order_time >= '2024-01-01'
    GROUP BY DATE(order_time)
)
SELECT * FROM daily_orders
ORDER BY order_date;

-- ✅ 避免SELECT *
SELECT order_id, user_id, amount
FROM orders
WHERE ...;

-- ✅ 使用分区裁剪
SELECT * FROM orders
WHERE pt = '202401';  -- MaxCompute
WHERE DATE_FORMAT(order_time, '%Y%m') = '202401';  -- ADB
```

### 3. 资源管理

| 数据库 | 资源配置建议 |
|--------|-------------|
| MaxCompute | 合理设置CU、合理分区 |
| ADB MySQL | 控制并发、使用读写分离 |
