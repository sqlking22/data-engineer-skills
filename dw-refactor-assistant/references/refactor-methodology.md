# 数仓重构方法论

> **本文件定位**：5 阶段重构框架的**导航骨架**。每阶段给出目标、产出物与 1-2 段概述，详细模板/脚本/规则在各自专题文件中展开。需要时按下方链接跳转，不要在对话开始时全部加载。

## 重构背景

### 烟囱式开发的典型问题

数仓在缺乏治理的快速迭代中，容易积累五类典型乱象，构成重构的驱动力：

1. **模型重复建设** — 同一业务逻辑有多个实现（如订单明细有 3 个版本），不同团队各自建表、命名随意，导致存储重复、维护成本数倍，数据口径不一致。
2. **依赖关系混乱** — ADS 层直接依赖 ODS 层（跨层依赖），任务依赖路径过长（10+ 层），存在循环依赖；导致数据质量无保障、任务失败影响面大、修改一处牵动全局。
3. **命名不规范** — 表名随意（`order_info_1`、`order_info_v2`、`tmp_order`），字段名随意（`amt`/`amount`/`total_amt`/`money`），无数据域归属；可读性差、无法统一管理、新人上手困难。
4. **缺少文档和负责人** — 表用途不明、字段含义不清、无责任人；知识流失、问题无人处理、无法追溯。
5. **资源浪费** — 孤儿表（无下游消费）、过期数据未清理、低效 SQL 未优化；存储与计算资源浪费、成本上升。

## 阶段1：现状盘点

**目标**：建立重构基线，知道"有什么"和"多乱"。

盘点覆盖三类资产（**表资产 / 任务资产 / 报表资产**），通过自动化扫描（`information_schema`、调度系统 API、SQL 解析）与访谈调研互补获取。问题按 Critical / Major / Minor 三级分类打分，结合影响范围倍率映射到 P0/P1/P2/P3 优先级。

**详细模板与脚本**：盘点字段清单、自动化扫描 SQL、访谈问卷、问题分类评分细则、优先级矩阵 —— 详见 **`asset-inventory-template.md`**。

---

## 阶段2：模型标准化

**目标**：建立规范体系，统一命名、分层、指标，生成旧→新的迁移映射。

本阶段对已有表采用"**反向归域**"方法（业务调研 → 表归类 → 域内整理 → 评审确认），将历史表归属到明确数据域；并制定命名规范与迁移映射表（旧表名/字段名 → 新名）。

> **职责边界**：本阶段聚焦"对存量资产执行标准化与生成迁移映射"——这是 dw-refactor 专属动作。
> **数据域划分方法论、总线矩阵、指标体系（原子/派生/衍生）的标准定义、分层规范、事实表/维度表设计** 属 modeling-assistant 职责，详见：
> - `modeling-assistant/references/onedata-methodology.md`（OneData：数据域、总线矩阵、指标体系）
> - `modeling-assistant/references/data-modeling-standards.md`（Kimball：分层、事实/维度表、SCD）
>
> dw-refactor 在此**消费**上述规范并应用到存量资产，不重新教授。

**迁移映射表**（旧名 → 新名 → 原因）是本阶段的核心产出，直接供阶段4渐进迁移消费。

---

## 阶段3：血缘与影响分析

**目标**：理清依赖关系（表级 / 任务级 / 字段级三层血缘），评估重构影响，制定迁移路径。

影响分析 5 步流程：确定变更内容 → 查询血缘图谱（上下游）→ 计算影响范围（直接/间接/业务）→ 评估风险等级（高/中/低）→ 制定应对措施（双跑验证、分批切换、通知下游等）。

**详细血缘解析方法、字段级血缘规则、影响分析报告模板** —— 详见 **`lineage-analysis-guide.md`**（血缘权威源）。

---

## 阶段4：渐进式迁移

**目标**：逐步迁移到新架构，保证业务连续性。

迁移遵循四原则：**业务连续性优先、渐进式分批、双跑验证、可回滚**。推荐大规模重构采用 **渐进式迁移 + 视图兼容过渡** 策略，5 个 Phase 依次推进：新模型建设 → 双跑验证 → 视图兼容 → 下游切换 → 旧模型下线。

**详细迁移阶段操作、双跑配置与对比脚本、视图兼容、切换顺序、回滚预案与脚本** —— 详见 **`migration-playbook.md`**。

> **职责边界**：本阶段执行迁移工程本身（迁移/双跑/切换/回滚）。
> 新模型的 **DDL 写法、MaxCompute vs ADB MySQL 方言、ETL INSERT 模板** 属 modeling-assistant / sql-assistant 职责，详见：
> - `modeling-assistant/references/model-design.md`（模型设计模板）
> - `sql-assistant/references/adb-mysql-guide.md` 与 `sql-assistant/references/maxcompute-guide.md`（方言对照）
> - `sql-assistant/references/sql-standards.md`（DDL/ETL 命名与语法）

---

## 阶段5：持续治理

**目标**：建立长效机制，防止再次烟囱化。

治理三大目标：**规范化**（统一标准）、**可追溯**（血缘清晰、责任明确）、**可复用**（公共沉淀、避免重复）。通过组织保障（角色 + 评审委员会）、流程保障（设计评审、变更审批、定期审计）、规范自动化检查、公共资产库与变更管控实现。

**详细治理组织、流程、自动化检查、公共资产库治理规则、变更分级、治理报告模板** —— 详见 **`governance-framework.md`**。

> **职责边界**：本阶段聚焦治理组织/流程/规范的落地。
> **数据质量检查规则**（任务失败率、新鲜度、空值率等规则定义与 SQL 实现）属 dq-assistant 职责，治理层订阅其告警结果，详见 `dq-assistant/references/data-quality-standards.md`。

## 重构成功标准

| 维度 | 指标 | 典型基线 | 目标 |
|------|------|---------|------|
| **结构** | 模型重复率 | 15% | < 2% |
| **结构** | 未归域表比例 | 25% | < 5% |
| **结构** | 命名不规范比例 | 35% | < 5% |
| **结构** | 跨层依赖数 | 35 | 0 |
| **效率** | 存储节省 | 基线 | 减少 30%+ |
| **效率** | 任务平均深度 | 12 层 | < 6 层 |
| **效率** | 新需求开发周期 | 5 天 | < 2 天（复用公共模型） |
| **质量** | 数据一致率 | 95% | > 99.9% |
| **质量** | 任务成功率 | 90% | > 99% |
